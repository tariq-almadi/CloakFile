# CloakFile

Upload a document, get back a **new** document in which sensitive information has
been replaced with stable placeholders.

```
ORIGINAL                                        SANITIZED
John Doe's phone number is 514-555-1234.        [PERSON_001]'s phone number is [PHONE_001].
His email is john.doe@example.com.              His email is [EMAIL_001].
His credit card is 4111 1111 1111 1111.         His credit card is [CREDIT_CARD_001].
```

The result is safe to hand to an external AI service, a vendor, or a support
ticket, because the sensitive values are no longer in the file.

> **Status: Phase 1 foundation.** The architecture, the security boundaries and
> a working TXT/CSV/JSON pipeline are in place. PDF and DOCX are deliberately
> unimplemented. This has not had a security review. See
> [Security limitations](#security-limitations) before using it with real data.

## Product principles

These are not preferences. They are the reason the product exists, and they
constrain every design decision in this repository.

**1. The document never leaves our infrastructure.**
No part of the core pipeline calls an external API. There is no LLM, no OCR
service, no telemetry. Detection is deterministic and runs locally. ESLint
blocks network and LLM imports inside `packages/` so this cannot erode by
accident.

**2. Replacement, not concealment.**
We distinguish three things and only promise the first two:

| Mode               | What it means                                                     | Acceptable? |
| ------------------ | ----------------------------------------------------------------- | ----------- |
| `text-replacement` | Original characters are gone; a placeholder stands in their place | Yes         |
| `content-removal`  | Original characters are gone entirely (metadata, annotations)     | Yes         |
| `visual-redaction` | Pixels cover the text; the text is still extractable              | **No**      |

A black rectangle over a name is not sanitization. The output is rebuilt as a
new file.

**3. We verify, then claim.**
Every sanitized document is re-read from its generated bytes and searched for
the values we said we removed. If any survive, the download is refused. "We
could not check" is reported as `inconclusive`, never as success.

**4. The browser sees as little as possible.**
The API has no field for an original value. The frontend receives placeholders
and masked previews (`Visa •••• 1111`), never `4111 1111 1111 1111`.

**5. Nothing is kept.**
Documents live in memory for the duration of one session and are then gone.
There is no database of documents and no permanent mapping of placeholders to
original values.

## Architecture at a glance

```
UPLOAD → VALIDATE → EXTRACT → DETECT → ASSIGN PLACEHOLDERS
       → [ user review ] → ANONYMIZE → GENERATE → VERIFY → DOWNLOAD → DELETE
```

An npm-workspaces monorepo. The frontend and the HTTP layer are thin; all the
real logic lives in framework-free packages.

```
apps/
  web/                    React + Vite + Tailwind. Rendering only.
  api/                    Fastify. Upload validation, sessions, HTTP mapping.
packages/
  shared/                 Types, errors, wire contract, privacy preview policy.
  detection/              Detector interface, registry, overlap resolution, detectors.
  anonymization/          Placeholder allocation and text rewriting.
  document-processing/    Format sniffing, extractors, generators.
  verification/           Proves the output no longer contains the originals.
  pipeline/               Composes the above. Knows nothing about HTTP.
tests/
  integration/            Cross-package round-trip and API tests.
  fixtures/               Synthetic sample documents.
docs/                     Architecture, security, threat model, development.
```

Full detail: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Prerequisites

| Tool    | Version              | Notes                                    |
| ------- | -------------------- | ---------------------------------------- |
| Node.js | **22.12.0 or newer** | See the note below if you are on 22.11.x |
| npm     | 10.9 or newer        | Ships with Node 22                       |

> **Node version note.** The toolchain (Vite, Vitest) declares
> `node >= 22.12.0`. The project currently runs on 22.11.x, but two things do
> not: Vite 8 (its native bundler binding is an optional dependency that npm
> silently skips on an engine mismatch) and `jsdom` (it needs `require(esm)`,
> added in 22.12). Both are avoided for now — see
> [docs/decisions/0002-toolchain-and-node-baseline.md](docs/decisions/0002-toolchain-and-node-baseline.md).
> Upgrading to Node 22.12+ or 24 LTS is recommended.

## Installation

```bash
git clone <repository-url>
cd cloakfile
npm install          # installs every workspace
cp .env.example .env # optional; sensible defaults apply without it
```

There are no API keys to obtain. That is deliberate.

## Environment setup

Everything has a working default, so `.env` is optional for local development.
Read [.env.example](.env.example) — each variable documents what it protects
against. The values most worth knowing:

| Variable                           | Default                 | Purpose                              |
| ---------------------------------- | ----------------------- | ------------------------------------ |
| `API_PORT`                         | `3001`                  | API listen port                      |
| `API_CORS_ORIGINS`                 | `http://localhost:5173` | Comma-separated allowlist. Never `*` |
| `UPLOAD_MAX_FILE_BYTES`            | `10485760` (10 MiB)     | Bounds per-request memory            |
| `SESSION_TTL_SECONDS`              | `900`                   | How long a document stays in memory  |
| `SANITIZATION_STRICT_VERIFICATION` | `true`                  | Refuse to release unverified output  |

Invalid configuration fails at startup rather than falling back to a permissive
default.

## Development commands

Run from the repository root.

| Command                 | What it does                                                |
| ----------------------- | ----------------------------------------------------------- |
| `npm run dev`           | Builds packages, then runs the API and the web app together |
| `npm run dev:api`       | API only, with watch mode, on `http://localhost:3001`       |
| `npm run dev:web`       | Web app only, on `http://localhost:5173`                    |
| `npm run build`         | Builds every package, the API and the web bundle            |
| `npm test`              | Runs the whole test suite                                   |
| `npm run test:watch`    | Tests in watch mode                                         |
| `npm run test:coverage` | Tests with a coverage report                                |
| `npm run typecheck`     | Type-checks every workspace, including tests                |
| `npm run lint`          | ESLint across the monorepo                                  |
| `npm run lint:fix`      | ESLint with autofix                                         |
| `npm run format`        | Prettier write                                              |
| `npm run verify`        | typecheck + lint + format check + test. Run before pushing  |

### Starting the frontend

```bash
npm run dev:web     # http://localhost:5173
```

It expects the API at `http://localhost:3001`; override with
`VITE_API_BASE_URL`.

### Starting the backend

```bash
npm run dev:api     # http://localhost:3001
curl http://localhost:3001/api/v1/health
```

The packages must be built at least once before the API can start
(`npm run build:packages`); `npm run dev` does this for you.

### Running tests

```bash
npm test                      # everything
npx vitest run packages/detection   # one package
npx vitest --project node     # node projects only
```

`npm test` builds the packages first, because the workspaces are consumed from
their compiled `dist` output.

## Project structure and ownership

Each area is self-contained, so two people can work in parallel without
touching each other's files.

| If you are working on                     | Work in                         | Depends on                                            |
| ----------------------------------------- | ------------------------------- | ----------------------------------------------------- |
| UI, upload flow, review screen            | `apps/web/`                     | `@cloakfile/shared`                                   |
| HTTP, uploads, sessions, security headers | `apps/api/`                     | `@cloakfile/pipeline`, `@cloakfile/shared`            |
| Finding PII                               | `packages/detection/`           | `@cloakfile/shared`                                   |
| Placeholders and replacement              | `packages/anonymization/`       | `@cloakfile/shared`                                   |
| PDF, DOCX, format handling                | `packages/document-processing/` | `@cloakfile/shared`                                   |
| Proving output is clean                   | `packages/verification/`        | `@cloakfile/shared`, `@cloakfile/document-processing` |
| The overall flow                          | `packages/pipeline/`            | all of the above                                      |
| Shared types and the API contract         | `packages/shared/`              | nothing                                               |

`packages/shared` is the one file set everyone touches. Changes there need a
review from another area owner — see [.github/CODEOWNERS](.github/CODEOWNERS).

## What works today

- TXT, CSV and JSON end to end: upload → detect → replace → verify → download
- Detectors: email, phone (international, via libphonenumber-js), credit card
  (Luhn + issuer validated), US SSN, IP address, URL, custom regex, and names /
  organizations via compromise
- Consistent placeholders: one value, one placeholder, throughout the document
- Post-generation verification with fail-closed behaviour
- Privacy-preserving review UI and API contract

## What is intentionally not built

- **PDF** and **DOCX** extraction and generation — registered, documented, and
  they fail loudly with `NOT_IMPLEMENTED`
- Address, government ID, bank account and date-of-birth detection — registered
  as stubs that report themselves as unimplemented
- OCR and scanned documents
- Authentication, accounts, persistence, multi-instance deployment

See [Phase 2](docs/DEVELOPMENT.md#phase-2-roadmap) for the plan.

## Security limitations

**This project has not had a security review and is not production-ready.**
Known limitations, in full, are in [docs/SECURITY.md](docs/SECURITY.md) and
[docs/THREAT-MODEL.md](docs/THREAT-MODEL.md). The most important ones:

- **Name detection is approximate.** compromise is a lexicon-based NLP library.
  It misses names it does not know and occasionally flags ordinary words. It is
  marked `experimental` in the UI for that reason. Never rely on automatic name
  detection alone for a high-stakes document.
- **Verification proves absence from extracted text, not from the file.** For
  plain text those are the same thing. For PDF and DOCX they will not be, which
  is one reason those formats are not enabled.
- **Uploads are buffered in memory**, which bounds file size and prevents
  horizontal scaling. This is a deliberate trade to avoid temporary files.
- **In-process erasure is best-effort.** Clearing a JavaScript `Map` does not
  guarantee the strings leave the heap.
- **No authentication or per-user isolation.** Anyone who can reach the API can
  submit a document.
