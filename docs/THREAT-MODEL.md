# Threat Model

> Scope: a React client, a Fastify API, and an in-memory ephemeral pipeline
> handling TXT, CSV, JSON and PDF. No authentication, no persistence, single
> instance.
>
> This model is written to be revisited. PDF support changed T-03 and T-14
> substantially; DOCX support will change T-04 and T-13 the same way.

---

## What we are protecting

| Asset                                 | Sensitivity                                                | Where it lives                              |
| ------------------------------------- | ---------------------------------------------------------- | ------------------------------------------- |
| The uploaded document                 | **Critical**                                               | API process memory, for the session TTL     |
| Detected values (`Detection.value`)   | **Critical**                                               | API process memory                          |
| The placeholder ↔ canonical-value map | **Critical**                                               | API process memory, one document's lifetime |
| The sanitized output                  | Moderate — should be safe, but only if sanitization worked | API memory, then the user's disk            |
| Placeholders and masked previews      | Low, by construction                                       | Sent to the browser                         |
| Availability of the service           | Moderate                                                   | —                                           |

## Who we are defending against

| Actor                      | Capability                            | Motivation                                                                  |
| -------------------------- | ------------------------------------- | --------------------------------------------------------------------------- |
| **Malicious uploader**     | Submits crafted files                 | Crash or exploit the parser, exhaust resources, escape the sandbox          |
| **Network attacker**       | Observes or modifies traffic          | Obtain documents in transit                                                 |
| **Other tenant / user**    | Uses the service normally             | Reach another user's document                                               |
| **Curious insider**        | Reads logs, metrics, dumps            | Obtain document contents without touching the app                           |
| **Compromised dependency** | Runs code in our process              | Exfiltrate documents                                                        |
| **The user themselves**    | Uploads a document, trusts the result | _(Not an attacker — but "incomplete sanitization" is the harm they suffer)_ |

## Trust boundaries

```
   ┌────────────┐   ① browser ↔ API      ┌──────────────────────────┐
   │  Browser   │ ◄──────────────────────►│  API process             │
   └────────────┘                         │                          │
                                          │  ② HTTP layer ↔ pipeline │
   ┌────────────┐   ③ file ↔ parser       │  ④ process ↔ host        │
   │  Uploaded  │ ───────────────────────►│     (memory, logs)       │
   │  document  │                         └──────────────────────────┘
   └────────────┘
```

① is the privacy boundary — see ARCHITECTURE §9.
③ is the exploitation boundary — everything past it is attacker-controlled data.

## Threats

Risk is assessed **as mitigated**.

### T-01 · Sensitive data exposure to the client

**Threat.** The API returns original values, and they appear in the review UI,
browser history, a screenshot or a client-side error report.

**Mitigations.**

- The wire schemas have no field for an original value — a type-level guarantee.
- `buildPreview` is the only sanctioned path from a value to client-visible
  text, driven by an exhaustive policy record (a missing type is a compile
  error). Credentials and government identifiers are `type-only`.
- Group ids are derived from the placeholder, not from the canonical key.
- Asserted in tests at the HTTP-payload level, not just at the unit level.

**Residual risk: Low.** A future endpoint could bypass the preview policy. Any
new response type carrying detection data needs review.

_This threat has already materialised once during development: the canonical
key, literally `CREDIT_CARD:4111111111111111`, was exposed as the group id. A
unit test caught it. The test is retained._

---

### T-02 · Incomplete sanitization

**Threat.** A sensitive value survives into the output and the user shares it
believing it is safe. **This is the most serious threat in the system**, because
the harm is caused by the user trusting a product that told them it worked.

**Mitigations.**

- Mandatory post-generation verification against the **generated bytes**.
- Fail-closed: `fail` and `inconclusive` both block the download.
- Normalised variant search, so a reformatted value is still found.
- A complementary check that the placeholders are actually present, so an empty
  output cannot pass trivially.
- `visual-redaction` output is rejected outright.
- Detector maturity is surfaced to the user; `experimental` and `stub`
  categories are labelled as such.

**Residual risk: Medium–High, and inherent.** Verification proves a value is
absent from the text we can _extract_. It cannot prove a value we never
detected is absent. **Detection recall is the ceiling on this guarantee.** A
name compromise does not recognise is never detected, never replaced, and
verification has no reason to look for it.

This is why the UI shows a reviewable list and why names are marked
experimental. It cannot be engineered away; it can only be communicated
honestly and improved with better detectors and adversarial testing.

---

### T-03 · Malicious upload / parser exploitation

**Threat.** A crafted file triggers memory corruption, resource exhaustion or
code execution in a parser.

**Mitigations.**

- Content-based format detection; extension and Content-Type are never trusted.
- Strict UTF-8 decoding with `fatal: true`; null bytes rejected.
- Non-Word ZIP archives rejected outright.
- Size limits at the parser, the application and the extraction layer.
- Uploads are never executed and never written to disk.
- Text parsers are `TextDecoder` and `JSON.parse` — a very small attack
  surface, both memory-safe.
- **PDF loading is funnelled through one hardened entry point**
  (`pdfjs-loader.ts`). Every network-shaped option is off (`useWorkerFetch`,
  range and streaming fetches, system fonts), scripting and XFA are off, WASM
  and the image decoders are off, `maxImageSize` is capped, and extraction runs
  under a time budget with page and object-count limits. Defaults are verified
  against the shipped bundle, never inherited — `maxImageSize` defaults to
  unbounded, which is exactly the kind of default this rule exists to catch.
- **Image decoding is avoided entirely.** Image-only pages are found by
  inspecting the PDF's object structure rather than by building an operator
  list, so a hostile JBIG2 or JPX payload is never handed to a decoder.

**Residual risk: Medium.** `pdfjs-dist` is a large, pure-JavaScript parser, so
memory-safety bugs are unlikely but denial of service through pathological
structure is not. The version floor is a security boundary: v6 removed the
eval-based font compilation behind CVE-2024-4367 outright. Before production,
run extraction in a separate process with a memory cap. Rises to **High** when
DOCX lands.

---

### T-04 · Decompression bomb

**Threat.** A small DOCX expands to gigabytes and exhausts memory.

**Mitigations.** `zip-guard.ts` reads the central directory without inflating,
and rejects on entry count, total declared size and compression ratio. It runs
today even though DOCX extraction does not.

**Residual risk: Medium.** Declared sizes are attacker-controlled. The guard is
a cheap pre-filter; a DOCX extractor must also cap bytes actually read from the
stream. Both layers are required.

---

### T-05 · Temporary file and memory exposure

**Threat.** Document contents are readable outside the application — a temp
file, a core dump, a swap page, a container layer.

**Mitigations.**

- **No temporary files at all.** This eliminates the entire temp-file class:
  permissions, crash residue, cleanup failures, path traversal.
- TTL-bounded in-memory sessions, swept automatically, deleted on user request,
  cleared on shutdown.
- `tmp/`, `uploads/`, `.env` and `*.log` are git-ignored.

**Residual risk: Medium.** Clearing a `Map` does not guarantee the strings leave
the heap; GC timing is not controllable. A core dump or swapped page could
contain document text. Disabling core dumps, encrypting swap and setting memory
limits are deployment concerns and **are not configured in this repository**.

_Note the trade:_ in-memory processing also caps file size and prevents
horizontal scaling. Moving to disk or a shared store to lift those limits would
reintroduce this threat, and is a decision to make deliberately.

---

### T-06 · Accidental sensitive logging

**Threat.** Document contents or detected values reach logs, and logs are
retained, shipped to a third party and read by people the user never consented
to.

**Mitigations.** Four independent layers — explicit serialisers, error-message
filtering with stack-header stripping, pino path redaction, and `no-console`
enforced by ESLint inside `packages/`. No third-party telemetry, and a comment
in `index.html` saying not to add any.

**Residual risk: Low–Medium.** A new library could log on its own. Log output
should be reviewed as part of any dependency addition.

---

### T-07 · Regular-expression denial of service

**Threat.** A crafted custom pattern, or a crafted document, causes catastrophic
backtracking and blocks the event loop.

**Mitigations.** Bounded quantifiers in all built-in patterns; a deliberately
non-RFC email pattern; `compileSafePattern` rejecting nested quantifiers,
quantified alternations, backreferences and lookbehind; caps on pattern length,
pattern count and text length.

**Residual risk: Medium.** The guard is a heuristic, not a proof, and a
synchronous regex cannot be interrupted once running. **Fix: run custom
patterns in a worker thread with a hard timeout.** On the Phase 2 list.

---

### T-08 · Denial of service through resource exhaustion

**Threat.** Large or numerous uploads exhaust memory or CPU.

**Mitigations.** Rate limiting; a 10 MiB default file cap enforced during
streaming; one file per request; bounded multipart fields; a 5 M character
extraction cap; `SESSION_MAX_ENTRIES` with **refusal rather than eviction**, so
a load spike cannot destroy another user's in-flight document.

**Residual risk: Medium.** Rate limiting is per-instance and in-memory. There is
no authentication, so limits apply per source address only. Detection over a
large document is CPU-bound and synchronous, so a few concurrent large uploads
can degrade latency.

---

### T-09 · Cross-user data access

**Threat.** One user retrieves another user's document.

**Mitigations.** Session ids are `randomUUID()` (122 bits of entropy),
unguessable and held only by the creating client. Sessions are keyed
individually with no enumeration endpoint.

**Residual risk: Medium.** **There is no authentication and no ownership
model.** Anyone who obtains a session id — from a shared screen, a proxy log, a
browser history entry — can fetch that document until it expires. Acceptable
for a single-user or trusted-network deployment; **not** acceptable for a
multi-tenant public service. Authentication is a prerequisite for that.

---

### T-10 · Dependency compromise

**Threat.** A malicious or compromised package exfiltrates documents from our
process.

**Mitigations.** A deliberately small dependency set; several utilities
implemented in-repo rather than installed; committed lockfile and `npm ci`;
`npm audit` in CI (currently 0 vulnerabilities); ESLint bans on network and LLM
imports inside `packages/`, which would make a naive exfiltration attempt fail
the build.

**Residual risk: Medium.** The ESLint ban is a development-time control, not a
runtime one — a transitive dependency can still open a socket. **No automated
dependency update or advisory pipeline is configured.** Runtime egress control
(network policy, egress-deny by default) belongs to deployment and is the only
real mitigation.

---

### T-11 · Transport interception

**Threat.** Documents are read or modified in transit.

**Mitigations.** CORS allowlist; `no-store` on downloads; `no-referrer`.

**Residual risk: High if deployed carelessly.** **This repository contains no
TLS configuration.** A deployment must terminate TLS, redirect or reject
plaintext, and set HSTS. Locally everything is loopback-bound.

---

### T-12 · CSRF and cross-site request abuse

**Threat.** A malicious page makes a user's browser submit or retrieve documents.

**Mitigations.** No cookies and no ambient credentials, so there is nothing to
ride. Session ids travel in the URL path and are held only by the creating
client. CORS is restricted to an origin allowlist.

**Residual risk: Low — conditional.** **This analysis is void the moment
cookie-based authentication is added.** Adding auth means adding CSRF protection
in the same change.

---

### T-13 · XXE and XML entity expansion

**Threat.** A DOCX contains an XML external entity that reads local files or
triggers a billion-laughs expansion.

**Status: not yet applicable.** No XML is parsed today.

**Required when DOCX lands:** external entity resolution disabled, DTD
processing disabled, entity expansion limits enforced. This must be verified,
not assumed from a library default.

---

### T-14 · PDF extraction and reconstruction limitations

**Threat.** A PDF is reported as sanitized while a value survives through a
channel the implementation did not cover.

**Primary mitigation: the output PDF is authored from scratch.** The uploaded
file is read, never edited. Text is extracted from every channel below,
sanitized, and written into a new document that inherits nothing — no fonts, no
images, no metadata, no attachments, no object history. A channel that is never
copied forward cannot leak, which turns "did we cover every hiding place?" into
"did we extract from every hiding place?". The second question is answerable;
the first is not.

**Known channels**, all extracted and all dropped from the output:
content-stream text, form field values, annotations (including their contents
and appearance text), `/Info` and XMP metadata, embedded files, outlines,
JavaScript actions, XFA, invisible OCR text layers (`3 Tr`), and prior
revisions retained by incremental updates. Where a channel is present in the
input, the user is told it was removed rather than sanitized.

**Secondary mitigation: verification does not trust the extractor.** The
`deep-streams` check inflates every stream in the output and decodes every
string in three encodings before searching; `structural-channels` confirms via
a second parser that no annotation, form, attachment, XMP packet, script,
outline or descriptive `/Info` entry survived. Both are described in
ARCHITECTURE §8.

**The limits that remain, and they are real:**

- A value present only as **pixels** is invisible to text extraction. Such
  pages are recorded in `ExtractedDocument.unreadable` and force an
  `inconclusive` result; the pipeline refuses to release the file under strict
  verification. There is no OCR, deliberately — OCR would produce a confident
  answer of unknown accuracy, which is worse than an honest refusal.
- **Layout is not preserved.** The output is paginated text, not a facsimile.
- **Non-Latin scripts degrade.** The output uses the standard Helvetica, so
  characters outside WinAnsi are written as `?` and the substitution is
  counted and reported.
- **Signatures are destroyed**, necessarily: a rebuilt document is a different
  document.

Drawing a rectangle over text remains unacceptable and unimplemented. The text
operator underneath is untouched and stays extractable; a covered value is a
present value.

---

### T-15 · Prototype pollution and injection

**Threat.** Crafted input manipulates `Object.prototype` or reaches an
interpreter.

**Mitigations.** All external input parsed through Zod schemas producing
known-shape objects; no recursive merging of user input; no `child_process`,
`eval`, `Function` or dynamic `require`; `no-proto`, `no-extend-native`,
`no-eval`, `no-implied-eval` and `no-new-func` are ESLint errors.

**Residual risk: Low.**

---

### T-16 · Path traversal via filename

**Threat.** A filename like `../../etc/passwd` escapes an intended directory.

**Mitigations.** **Structurally eliminated in Phase 1**: no file is ever written
to disk, and storage is keyed by a generated UUID. The filename is additionally
normalised through a character allowlist because it reaches a
`Content-Disposition` header and the DOM.

**Residual risk: Low.** Rises if disk-backed storage is introduced.

## Before production

1. Terminate TLS and reject plaintext (T-11).
2. Add authentication and an ownership model (T-09).
3. Move custom regex execution into a worker with a timeout (T-07).
4. Configure runtime egress control (T-10).
5. Disable core dumps, configure memory limits and swap (T-05).
6. Adversarially test detection recall with realistic documents (T-02).
7. Run PDF extraction in a separate process with a memory cap and a hard kill,
   so a pathological document degrades one request rather than the service
   (T-03, T-08).
8. Test PDF handling against a corpus of real-world and adversarial files. The
   fixtures in this repository are ones we wrote, which means they exercise the
   failure modes we already thought of (T-03, T-14).
9. Commission an independent security review, especially of PDF, and of DOCX
   once written (T-03, T-13, T-14).
